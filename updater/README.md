# TSSUpdater

Модуль обновлений Windows x64 под лицензией MIT. Самостоятельный TSSLogViewer
использует канал `viewer`, общий установщик TSSLimiterX + TSSLogViewer — `suite`.
Модуль Qt подключается к обоим приложениям; отдельный `TSSUpdater.exe` собран
со статическим CRT и не зависит от заменяемых библиотек Qt.

## Поведение

- Проверка через 10 секунд после запуска, затем раз в сутки, пока приложение
  открыто. Настройки проверки и загрузки по умолчанию включены. Ручная проверка —
  через «Обновления программ…». Сетевые ошибки в фоне не открывают окна.
- Скачиваются только файлы с изменившимся SHA-256. Неизменившиеся DLL повторно
  не скачиваются; изменившийся файл скачивается целиком. Это обновление по файлам,
  а не двоичные патчи.
- Обе программы используют общий кэш и настройки для конкретного каталога
  установки. Установка начинается после «Обновить и перезапустить».
  Нужно закрыть вторую программу и закончить работу с устройствами. Процессы
  принудительно не завершаются; ожидание закрытия ограничено двумя минутами.
- Ярлыки запускают native helper, который блокирует загрузку Qt во время замены
  файлов. После установки возвращается исходная программа без повышения прав.
- Обновление в Program Files вызывает UAC. Portable-каталог, доступный на запись,
  обновляется без повышения. Повышенные обновления разрешены только внутри
  защищённого Program Files; произвольный каталог для установки «всем пользователям»
  не поддерживается. Программы следует запускать обычным пользователем.
- Настройки, логи и прочие файлы пользователя не удаляются. Удаляются только
  устаревшие файлы, перечисленные в предыдущем подписанном выпуске.
- Перед заменой создаются проверенные резервные копии и журнал. Ошибка вызывает
  откат; после аварии или отключения питания запуск через ярлык / `TSSUpdater.exe`
  восстанавливает предыдущую установку. Резервная копия остаётся в `.tss-update`.
  Ручного выбора старых выпусков в интерфейсе пока нет.

Linux/macOS этот модуль пока не используют. Повторная первоначальная установка
через Inno Setup нужна один раз для перехода со старых версий без TSSUpdater.

## Доверие и формат

`keys/release-public.txt` содержит публичный RSA-3072 ключ в формате CNG
`BCRYPT_RSAPUBLIC_BLOB` (Base64). Закрытый ключ хранится вне Git. Файлы `*-private.pem`
игнорируются. Не заменяйте ключ при каждом выпуске: уже установленные приложения
доверяют закреплённому ключу.

`latest.tssupdate`: первая строка — Base64 подписи RSA-PSS/SHA-256, остальное —
подписанный UTF-8 манифест с LF. В нём фиксированы продукт, монотонный `sequence`,
срок действия (по умолчанию 180 дней), версии обеих программ, минимальный runtime,
описание выпуска и список `file<TAB>размер<TAB>sha256<TAB>путь`.
Точный подписанный манифест первоначальной установки лежит в `TSSUpdate.manifest`.

Проверяются HTTPS, подпись, срок действия, продукт, отсутствие понижения версий,
SHA-256 каждого файла и допустимость путей. Повышенный процесс повторяет проверки
после копирования из пользовательского кэша. Подпись пакета не является Windows
Authenticode и сама по себе не устраняет предупреждения SmartScreen.

## GitHub Actions и ключ

В **обоих** репозиториях добавьте Actions secret `TSS_UPDATE_PRIVATE_KEY` с одинаковым
PEM закрытого ключа, соответствующего `keys/release-public.txt`. Например, передайте
файл в `gh secret set TSS_UPDATE_PRIVATE_KEY --repo OWNER/REPO < secret-private.pem`
из cmd.exe на доверенной машине. Секрет не выводить в журнал или чат.
Ключ храните также в защищённой резервной копии вне каталогов сборки.

Обычная сборка без секрета допускается, но автоматические обновления в таком
пакете отключены. `release.yml` требует подпись и завершится ошибкой без ключа.
Тесты используют отдельный временный ключ и не подписывают тестовые данные
ключом выпуска. Перед публикацией нужно закоммитить изменения в репозитории
просмотрщика и отдельно обновить его указатель в TSSLimiterX.

Артефакты: `TSSLimiterX-windows-update.zip` в общем репозитории и
`TSSLogViewer-windows-update.zip` в самостоятельном просмотрщике. В ZIP находятся
`latest.tssupdate` и `blobs/<sha256>.bin`. Общий пакет включает обе программы,
исходники просмотрщика, лицензии, переводы и при необходимости новый VC Runtime.

## Размещение на сайтах

На обоих HTTPS-серверах `tsslimiter.com` и `tsslimiter.ru`:

| Пакет | Каталог |
| --- | --- |
| Общий TSSLimiterX + TSSLogViewer | `/updates/windows/suite/` |
| Отдельный TSSLogViewer | `/updates/windows/viewer/` |

1. Распакуйте пакет вне публичного каталога. Проверьте канал и версии. `sequence`
   должен быть больше ранее опубликованного; версии обоих компонентов не понижать.
2. Загрузите новые `blobs/*.bin` на оба зеркала. Старые blobs пока сохраняйте:
   пользователи могут заканчивать ранее начатое скачивание.
3. Только после завершения загрузки замените `latest.tssupdate` атомарным
   переименованием на каждом зеркале. Не меняйте содержимое подписанного файла.
4. Для манифеста задайте `Cache-Control: no-cache`; для blobs допустим долгий
   immutable-кэш. Отдавайте файлы без авторизации, HTML-заглушек и перенаправлений
   на другой домен. Подойдут `application/octet-stream` и корректный Content-Length.
5. Проверьте установку предыдущего подписанного выпуска и обновление через меню
   каждой программы. Выпуск в GitHub сам по себе ничего на этих сайтах не публикует.

В этой версии нет загрузки на хостинг из Actions: артефакты передаются процессу
публикации сайта. Релиз необходимо обновить до истечения 180 дней, даже если версии
EXE не менялись: новый `sequence` и подпись продлевают доступность обновлений.

## Локальная сборка пакета

PowerShell 7, готовая папка Windows-программы с helper, DLL, лицензиями и VERSION.txt:

```powershell
./updater/tools/New-UpdatePackage.ps1 -SourceDir ./dist/viewer -OutputDir ./build/feed `
  -Product tss-viewer-windows-x64 -Version 26.2 -ViewerVersion 26.2 `
  -PrivateKeyPath C:/secure/release-private.pem -Notes 'Описание выпуска'
```

Скрипт добавляет `TSSUpdate.lock` и подписанный `TSSUpdate.manifest` в исходную папку.
Для suite нужны также `TSSLimiterX.exe` и `TSSLogViewer-VERSION.txt`. Параметры
`-RuntimePath` и `-RuntimeVersion` добавляют prerequisite, который скачивается и
устанавливается только при недостаточной версии Microsoft VC Runtime.
`-AllowUnsignedBuild` разрешает локальную проверку упаковки без подписи.

## Проверки

```powershell
./updater/tools/New-UpdateKey.ps1 -PrivateKeyPath ./build/test-private.pem -PublicKeyPath ./build/test-public.txt
cmake -S updater -B build/tests -G Ninja -DCMAKE_BUILD_TYPE=Release `
  -DTSS_UPDATER_BUILD_CLIENT=OFF -DTSS_UPDATER_BUILD_TESTS=ON `
  -DTSS_UPDATE_PUBLIC_KEY="$PWD/build/test-public.txt"
cmake --build build/tests
ctest --test-dir build/tests --output-on-failure
./updater/tests/integration.ps1 -Updater ./build/tests/TSSUpdater.exe `
  -CoreTests ./build/tests/tss_update_tests.exe -PrivateKey ./build/test-private.pem `
  -PublicKey ./build/test-public.txt -Workspace ./build/integration
```

Интеграционный сценарий требует новый каталог для каждого запуска. Если терминал
повышен (например, GitHub Windows runner), каталог проверки должен быть внутри
Program Files. Проверяются подпись, подмена, повреждение загрузки, занятие DLL,
откат, восстановление журнала, ожидание приложения, замена самого helper,
удаление устаревших файлов, сохранение пользовательских данных и запрет понижения.

## macOS: Sparkle

Обе программы подключают Sparkle 2.10.0. CMake загружает закреплённый архив с
проверкой SHA-256 и встраивает полный framework с XPC-компонентами. Для сборки
нужны macOS 12+, Qt, Ninja и инструменты Xcode. Подпись вложенных компонентов
выполняет `tools/sign-macos.py` до нотарификации внешнего приложения.

Пункт меню обновлений открывает настройки проверки и фоновой загрузки; кнопка
проверки запускает стандартный интерфейс Sparkle. Приложение откладывает перезапуск,
пока подключены устройства или открыта операция с прошивкой.

`TSS_SPARKLE_PRIVATE_KEY` в GitHub Secrets содержит base64 от 32-байтового seed
Ed25519, экспортируемого современным `generate_keys`. Открытый ключ —
`keys/sparkle-public.txt`, он встроен в Info.plist. Sparkle требует подписи
ленты и проверяет архив до распаковки. Закрытый ключ передаётся `sign_update`
через stdin, в репозиторий и артефакты не попадает.

Основной репозиторий готовит нотарифицированные пакеты для каналов `limiter`
и `viewer`. Самостоятельный публичный CI просмотрщика использует отдельный
канал `viewer-community` с ad-hoc подписью. Нельзя смешивать эти ленты:
производственную сборку просмотрщика нельзя заменять пакетом публичного CI.

Для ручной установки обеих программ выпускаются DMG: в окне Finder приложение
слева, папка «Программы» справа и стрелка между ними. Перетащите приложение в
«Программы», затем запускайте его оттуда. Внутри образа имя `.app` не содержит
версии. Общий CI подписывает и нотарифицирует как приложение, так и готовый DMG;
публичный CI просмотрщика создаёт DMG с приложением с ad-hoc подписью.

Образы создаёт `packaging/macos/create-dmg.py` с закреплённой версией `dmgbuild`
из `requirements-dmg.txt`. Оформление записывается без запуска Finder в CI.
После создания образ монтируется только для чтения: проверяются ссылка на
`/Applications`, настройки окна, Info.plist и подпись скопированного приложения.
Для автоматического обновления отдельно создаётся ZIP из того же приложения;
ручная установка через DMG не меняет формат ленты Sparkle.

Пакет `<программа>-macos-update.zip` содержит `files/` и два подписанных
`appcast.xml` — отдельно для tsslimiter.com и tsslimiter.ru. На каждом зеркале:

1. Скопируйте `files/` в `/updates/macos/<канал>/files/`.
2. После загрузки архивов атомарно замените `/updates/macos/<канал>/appcast.xml`
   файлом из каталога соответствующего домена. Не редактируйте подписанный XML.
3. Для ленты отключите кэширование; архивам разрешите immutable-кэш.

Sparkle устанавливает архив `.app` без повторного установщика. Текущая упаковка
создаёт полные архивы; генерация бинарных `.delta` из предыдущего выпуска пока
не подключена. При сетевой ошибке следующая проверка меняет зеркало.

## Linux: AppImageUpdate

В AppImage включён оригинальный `appimageupdatetool` из выпуска
`2.0.0-alpha-1-20251018`, проверяемый по SHA-256. Он работает отдельным процессом
над временной копией AppImage; FUSE для вложенного helper не требуется.
После загрузки программа проверяет размер и SHA-256 по RSA-PSS-подписанным
данным. Используется тот же ключ `TSS_UPDATE_PRIVATE_KEY`, что в Windows;
`keys/release-public.pem` — PEM-представление существующего открытого RSA-ключа.

Проверка выполняется при запуске и затем раз в сутки; фоновую загрузку можно
отключить в окне обновлений. Для установки нужны права записи на AppImage и
его каталог. Каталог настроек и логи не заменяются. Прежний AppImage сохраняется
рядом как `*.backup`; новый файл устанавливается через атомарный `QSaveFile`,
после чего приложение перезапускается. При отказе запуска резервная копия
остаётся доступной. Символические ссылки не обновляются.

Пакет `<программа>-linux-update.zip` содержит `files/`, `latest.tssupdate`,
`latest.AppImage.zsync` и `publication.json`. Для обоих доменов:

1. Загрузите `files/` в `/updates/linux/limiter/` либо `/updates/linux/viewer/`.
2. Замените `latest.AppImage.zsync` и последним — `latest.tssupdate`.
3. Сервер должен поддерживать HTTP Range для экономии трафика. Не меняйте
   AppImage и `.zsync` после упаковки. Старые файлы оставьте для начатых загрузок.

`.upd_info` содержит стабильный адрес `.zsync` для внешнего AppImageUpdate.
Встроенный клиент сначала проверяет собственный подписанный манифест и использует
указанный в нём неизменяемый `.zsync`. Срок действия манифеста — 180 дней.
Если сеть или загрузка недоступны, рабочая версия остаётся на месте.

## Сборка и проверка платформенных обновлений

`TSS_UPDATE_BUILD` — возрастающий Unix timestamp сборки, передаваемый CI в CMake.
На macOS он представлен тремя числовыми частями CFBundleVersion; пользовательская
версия остаётся `PROJECT_VERSION`. Номер сохраняется в `UPDATE_BUILD.txt`.
При повторной локальной сборке CMake сохраняет закэшированный номер; для нового
выпуска передайте новый `-DTSS_UPDATE_BUILD=...`.

`tools/platform-package.py` подготавливает подписанные ZIP для сайта. Скрипт
ничего не загружает на хостинг. Без секретов обычная проверочная сборка выдаёт
только переносимый пакет; `release.yml` требует подписи и останавливается при
отсутствии нужного ключа.

Проверки Linux-протокола с независимым временным ключом:

```bash
cmake -S updater/tests/platform -B build-platform-tests -G Ninja
python3 updater/tests/platform/fixtures.py build-platform-tests/fixtures
cmake --build build-platform-tests
ctest --test-dir build-platform-tests --output-on-failure
```

Проверяются подпись, подмена данных, другой продукт/архитектура, срок действия,
понижение версии, пути пакетов, повреждённая загрузка, атомарная замена и сохранение
резервной копии. Перед первым выпуском дополнительно проверьте на настоящих
macOS/Linux: обновление старой сборки, обрыв сети, нехватку прав/места и запрет
перезапуска при подключённом устройстве. Старые выпуски без этого механизма
нужно один раз заменить новой сборкой вручную.
